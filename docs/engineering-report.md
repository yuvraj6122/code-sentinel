# Engineering Report Generator

The Engineering Report Generator consolidates everything CodeSentinel already
knows about a repository — metadata, every agent's findings, and the AI Planning
Agent's recommendations — into a single, human-readable **Markdown** report.

It is a **read-only consumer**. It never re-runs repository analysis and never
regenerates recommendations; it renders data that a completed analysis already
persisted.

## Workflow

```
GET /api/analyses/{analysisId}/report
        │
        ▼
ReportGeneratorService
  ├─ load Analysis (+ repository, findings)      ← AnalysisRepository
  ├─ load Recommendations (priority order)       ← RecommendationRepository
  ├─ assemble a format-agnostic ReportModel      ← grouping, tallies, health
  └─ render it                                    ← ReportRenderer
        │
        ▼
MarkdownReportRenderer → ReportDocument(fileName, markdown)
```

All report-building logic (severity tallies, per-category grouping, the health
grade, the conclusion) lives in the **assembly** step and produces a
`ReportModel`. Rendering only formats that model. This split is what lets a new
format (e.g. PDF) be added later by implementing a second `ReportRenderer`
without touching the assembly logic.

### Key types (backend)

| Type | Responsibility |
| --- | --- |
| `ReportGeneratorService` / `…Impl` | Retrieve analysis, findings, recommendations; assemble the model; return rendered `ReportDocument`. |
| `ReportModel` | Immutable, format-agnostic representation of the whole report. |
| `SeverityBreakdown` | Critical/High/Medium/Low tally, reused overall and per category. |
| `ReportRenderer` (interface) | Renders a `ReportModel` to a string. |
| `MarkdownReportRenderer` | GitHub-flavoured Markdown renderer. |
| `ReportDocument` | Suggested download file name + rendered content. |
| `ReportController` | `GET /api/analyses/{analysisId}/report`. |

## Report structure

The Markdown report always contains these nine sections, in order:

1. **Report Header** — repository name, URL, analysis ID, status, analysis date.
2. **Executive Summary** — repository health grade, AI overall assessment (if
   present), total findings, and a severity breakdown table.
3. **Repository Overview** — name, language, build tool, and finding-derived
   statistics.
4. **Complexity Analysis** — severity table, most critical files, findings.
5. **Security Analysis** — severity table, most critical files, findings.
6. **Testing Analysis** — severity table and testing-quality findings (framework
   detection, disabled tests, missing integration tests, assertion/naming
   quality).
7. **Duplicate Code Analysis** — severity table, most duplicated files, findings.
8. **AI Recommendations** — overall assessment plus each prioritized
   recommendation's impact, affected categories, description, and reasoning.
9. **Conclusion** — strengths, primary risks, and recommended next steps.

Findings are listed severity-first and capped per category to keep the report
readable; the full counts are always shown in the severity tables.

### Data sources

The report uses only **persisted** data reached from the `analysisId`:

- `Analysis` (status, timestamps, `overallAssessment`)
- `RepositoryEntity` (name, URL, language, build tool)
- `Finding`s (per-category, with severity and file/line)
- `Recommendation`s (priority-ordered, with impact and affected categories)

> Source/test file counts and the numeric testing maturity score are computed
> transiently during analysis and are not persisted, so the report reflects them
> through the findings rather than as standalone metrics.

## API

```
GET /api/analyses/{analysisId}/report
GET /api/analyses/{analysisId}/report?download=true
```

- Returns `200 OK` with `Content-Type: text/markdown; charset=UTF-8` and the
  report body.
- With `?download=true`, adds `Content-Disposition: attachment; filename="…"`
  so browsers download it as a `.md` file.
- Returns `404 Not Found` (JSON error, via the shared exception handler) when the
  analysis id does not exist.

Recommendations are **not** regenerated by this endpoint. If none exist, the AI
Recommendations section explains how to generate them.

## Supported output format

Markdown today. The `ReportRenderer` abstraction is designed so additional
formats (such as PDF) can be added later by implementing the interface against
the same `ReportModel`, with no change to report assembly.

## Frontend

The dashboard's **Engineering Report** section (`ReportSection`) offers a
"Generate Report" action that calls the endpoint for the current `analysisId`,
then lets the user:

- view the rendered Markdown,
- copy it to the clipboard,
- download it as a `.md` file.

It reuses the existing `DashboardSection`, `ErrorBanner`, and `LoadingSpinner`
components and reads existing analysis data only.
